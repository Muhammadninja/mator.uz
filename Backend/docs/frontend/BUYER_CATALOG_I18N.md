# BUYER_CATALOG_I18N.md — покупательское приложение: локализованные категории

**Аудитория:** команда мобильного приложения (buyer app).
**Статус backend:** реализовано, тесты зелёные, миграция БД **написана, но ещё
не применена** — см. [§8](#8-порядок-выката).
**Связанные документы:**
`FRONTEND_REQUIREMENTS.md` (админ-панель: как названия ЗАВОДЯТСЯ) ·
`ADMIN_FRONTEND_SPEC.md` (полный контракт админских эндпоинтов) ·
`../../category_translations.json` (готовое дерево категорий с переводами).

---

## 1. Что изменилось в двух словах

Раньше buyer API отдавал название категории **одной строкой** — внутренним
полем `name`. Оно английское для всех засеянных категорий («Brake pads»,
«Motor oil»), поэтому русский и узбекский покупатель видели английский текст.

Теперь backend **сам** отдаёт название на языке запроса. Приложению не нужно
хранить словарь категорий и не нужно выбирать перевод самостоятельно.

| Было | Стало |
|---|---|
| `category.name` — то, что рендерил клиент | `category.label` — то, что рендерит клиент |
| — | `category.name` остался, но он **внутренний**: не показывать |
| — | язык берётся из заголовка `Accept-Language` |

**Что нужно сделать фронтенду:**

1. Слать `Accept-Language` на всех запросах каталога.
2. Везде, где сейчас рендерится `category.name`, рендерить `category.label`.
3. В поиске перестать использовать название категории как идентификатор —
   для этого появился `id` (см. [§5](#5-поиск--важное-изменение)).

## 2. Как передавать язык

Стандартный HTTP-заголовок на каждом запросе:

```http
Accept-Language: ru
Accept-Language: uz
Accept-Language: en
```

Поддерживаются три языка: `ru`, `uz` (латиница), `en`.

**Отдельного query-параметра `?lang=` нет и не планируется.** Заголовок —
единственный механизм (единственное исключение — `POST /v1/search`, см. ниже).

### Что backend принимает

| Заголовок | Результат |
|---|---|
| `ru`, `uz`, `en` | как есть |
| `ru-RU`, `uz-UZ`, `en-US`, `uz-Latn-UZ` | регион отбрасывается → `ru` / `uz` / `en` |
| `RU`, `  en  ` | регистр и пробелы не важны |
| `de-DE,uz;q=0.9,ru;q=0.5` | учитывается `q` → `uz` |
| `uz;q=0` | явный отказ от языка — `uz` отбрасывается |
| `*` | язык по умолчанию |
| заголовок отсутствует | язык по умолчанию |
| `de-DE` (не поддерживается) | язык по умолчанию |
| мусор (`;;;`, `ru;q=abc`) | не 500 — язык по умолчанию |

**Язык по умолчанию — `ru`.**

Гарантия: **никакой заголовок не приводит к 500 и не даёт пустой label.**
Можно не слать заголовок вообще — приложение продолжит работать как сейчас,
на русском.

### Рекомендация по значению

Слать язык интерфейса приложения, а не язык устройства — это то, что
пользователь выбрал явно:

```ts
const headers = { 'Accept-Language': i18n.language }; // 'ru' | 'uz' | 'en'
```

## 3. Где появился `label`

Поле `label` — **это то, что нужно показывать пользователю.**

### 3.1 `GET /v1/categories` — главная сетка

```jsonc
{
  "items": [
    {
      "id": "brakes",              // стабильный идентификатор
      "name": "Brakes",            // ВНУТРЕННЕЕ — не показывать
      "label": "Тормоза",          // ← показывать это
      "name_ru": "Тормоза",
      "name_uz": "Tormozlar",
      "name_en": "Brakes",
      "slug": "brakes",
      "count": 12,
      "iconKey": "brake",
      "color": "#f00"
    }
  ],
  "total": 12
}
```

При `Accept-Language: uz` тот же запрос вернёт `"label": "Tormozlar"`.
`id`, `slug`, `count`, порядок элементов — **одинаковы на всех языках**.

> При `?scope=vehicle` `label` тоже присутствует, но равен `name`: этот список
> берётся из захардкоженной таблицы с одним названием. Поле есть, чтобы клиент
> читал `label` единообразно в обоих режимах и не ветвился.

### 3.2 `GET /v1/catalog/parts` и `GET /v1/catalog/parts/:id`

```jsonc
{
  "category": {
    "id": "brake-pads",
    "name": "Brake pads",              // ВНУТРЕННЕЕ — не показывать
    "label": "Тормозные колодки",      // ← показывать это
    "name_ru": "Тормозные колодки",
    "name_uz": "Tormoz kolodkalari",
    "name_en": "Brake pads"
  }
}
```

### 3.3 Чипы подкатегорий (`subcategories` в листинге)

```jsonc
{
  "id": "oil-filters",
  "name": "Oil filters",          // ВНУТРЕННЕЕ
  "label": "Масляные фильтры",    // ← показывать это
  "title_ru": "Масляные фильтры",
  "title_uz": "Moy filtrlari",
  "title_en": "Oil filters",
  "count": 7
}
```

`title_ru` / `title_uz` / `title_en` **сохранены** — существующий код,
который их читает, продолжит работать. Ничего не удалено.

## 4. Зачем нужны и `label`, и три имени

`label` — это выбор, уже сделанный сервером для **текущего** запроса.
`name_ru` / `name_uz` / `name_en` остаются рядом для одного случая:
пользователь переключил язык в приложении, а карточка товара **уже лежит в
кэше**. Тогда можно перерисовать её из локального поля, не делая повторный
запрос.

```ts
// обычный рендер
<Text>{part.category.label}</Text>

// перерисовка кэшированной карточки после смены языка
const local = { ru: 'name_ru', uz: 'name_uz', en: 'name_en' }[lang];
<Text>{part.category[local] ?? part.category.label}</Text>
```

Если такой оптимизации нет — просто всегда читайте `label` и игнорируйте
остальные поля.

## 5. Поиск — важное изменение

### 5.1 Что было сломано

`POST /v1/search` возвращал фасет категорий, **ключами которого были названия**:

```jsonc
// БЫЛО
{
  "facetCounts": { "categories": { "Brake pads": 12, "Motor oil": 7 } },
  "suggestedCategories": ["Brake pads", "Motor oil"]
}
```

Русский покупатель получал английские подписи. Хуже: если клиент использовал
эту строку как идентификатор — она теперь **меняется вместе с языком**.

### 5.2 Что стало

```jsonc
{
  "results": [
    {
      "id": "part_1",
      "title": "Bosch brake pad set",
      "price": "UZS 185 000",
      "category": "Тормозные колодки",   // локализовано
      "category_id": "brake-pads"        // НОВОЕ — стабильный id
    }
  ],
  "facetCounts": {
    "categories": { "Тормозные колодки": 12, "Моторное масло": 7 }
  },
  "categories": [                        // НОВОЕ — предпочтительный формат
    { "id": "motor-oil",  "name": "Моторное масло",     "count": 7 },
    { "id": "brake-pads", "name": "Тормозные колодки",  "count": 12 }
  ],
  "suggestedCategories": ["Моторное масло", "Тормозные колодки"]
}
```

**Изменения:**

| Поле | Что с ним |
|---|---|
| `facetCounts.categories` | форма та же, но **ключи локализованы** |
| `suggestedCategories` | значения **локализованы**, порядок — по убыванию `count` |
| `categories` | **новое**, массив `{id, name, count}` — используйте его |
| `results[].category` | **локализовано** |
| `results[].category_id` | **новое**, стабильный id |

### 5.3 Правило, которое нужно усвоить

```text
id    = идентификатор  (стабилен, одинаков на всех языках)
label = подпись        (меняется вместе с языком)
```

**Никогда не используйте локализованную подпись как идентификатор** — ни в
фильтрах, ни в ключах кэша, ни в аналитике, ни в дип-линках.

Фильтр по категории всегда принимал **id**, а не название:

```jsonc
{ "query": "тормоз", "filters": { "categories": ["brake-pads"] } }
```

Это не изменилось. Поэтому ключи `facetCounts.categories` **никогда** не
годились для обратной подстановки в фильтр — теперь для этого есть
`categories[].id`.

### 5.4 Миграция клиента

```ts
// БЫЛО — ломается при смене языка
const selected = Object.keys(res.facetCounts.categories)[0];
filters.categories = [selected];

// СТАЛО
const selected = res.categories[0];
filters.categories = [selected.id];   // id — в запрос
label = selected.name;                // name — на экран
```

### 5.5 Язык для поиска

`POST /v1/search` принимает язык **двумя** способами:

1. поле `locale` в теле запроса (`"locale": "uz"`) — **приоритетнее**;
2. заголовок `Accept-Language` — если `locale` не прислан.

Поле `locale` уже было в DTO, но не использовалось. Оно существует для случая,
когда язык интерфейса приложения отличается от языка устройства.

## 6. Что осталось без изменений

Ничего не удалено и не переименовано. Backward compatibility сохранена:

- `category.name` — на месте (стал внутренним, но не удалён);
- `name_ru` / `name_uz` / `name_en` — на месте;
- `title_ru` / `title_uz` / `title_en` в чипах — на месте;
- `facetCounts.categories` — форма объекта не изменилась;
- фильтры, сортировка, пагинация, счётчики — **не зависят от языка**;
- id категорий, slug'и, порядок элементов — **одинаковы на всех языках**.

Клиент, который не пришлёт `Accept-Language` и не тронет ни строчки, продолжит
получать русские подписи и работать как раньше.

## 7. Чек-лист приёмки

- [ ] `Accept-Language` отправляется на `/v1/categories`,
      `/v1/catalog/parts`, `/v1/catalog/parts/:id`, `/v1/search`.
- [ ] Главная сетка рендерит `label`, а не `name`.
- [ ] Карточка товара рендерит `category.label`.
- [ ] Чипы подкатегорий рендерят `label`.
- [ ] Поиск рендерит `categories[].name`, а фильтрует по `categories[].id`.
- [ ] Нигде название категории не используется как ключ/идентификатор.
- [ ] Смена языка в приложении меняет подписи категорий (проверить все три).
- [ ] `ru-RU` / `uz-UZ` / `en-US` работают так же, как `ru` / `uz` / `en`.
- [ ] Без заголовка приложение работает и показывает русский.
- [ ] Счётчики и порядок категорий не меняются при смене языка.

## 8. Порядок выката

Миграция `20260818000000_category_i18n_and_seller_lang` добавляет колонки
`name_ru` / `name_uz` / `name_en`. **Она ещё не применена** — на dev-базе этих
колонок нет, backend отстаёт на несколько миграций.

Порядок:

1. применить миграцию + сиды переводов;
2. выкатить backend;
3. выкатить клиент.

Клиент можно выкатывать и раньше — до шага 2 он получит русские подписи
(язык по умолчанию), а не ошибку. Обратный порядок (клиент до backend) тоже
безопасен: неизвестный заголовок игнорируется.

---

## 9. Чего делать НЕ нужно

- **Не** хранить словарь названий категорий на клиенте — сервер уже отдаёт
  готовую подпись.
- **Не** показывать `category.name` пользователю.
- **Не** добавлять `?lang=` — его нет.
- **Не** использовать локализованную подпись как id, ключ кэша или значение
  фильтра.
- **Не** переводить названия категорий на клиенте — переводы заводятся
  операторами в админ-панели и являются источником истины.
