# FRONTEND_REQUIREMENTS.md — админ-панель: локализованные названия категорий

**Аудитория:** команда фронтенда админ-панели.
**Статус backend:** реализовано в ветке `feature/seller-i18n-and-categories`.
Миграция БД **написана, но ещё не применена** к продакшену — см.
[§9](#9-порядок-выката).
**Связанные документы:**
`Backend/docs/frontend/ADMIN_FRONTEND_SPEC.md` (полный контракт админских
эндпоинтов; этот файл углубляет только раздел названий категорий) ·
`category_translations.json` (готовое дерево категорий с переводами).

---

## 1. Что изменилось в двух словах

У категории было **одно** отображаемое имя `name`. Стало **три обязательных**:

| Было | Стало |
|---|---|
| `name` — то, что видел пользователь | `nameRu`, `nameUz`, `nameEn` — то, что видит пользователь |
| — | `name` остался, но стал **внутренним** (slug, сортировка, логи) |

Причина: категорию видят три разные аудитории — покупательское приложение в
своей локали, Telegram-бот продавца на выбранном продавцом языке и сама
админ-панель. Категория без имени на одном из языков рендерится как **пустая
кнопка** у всех пользователей этого языка, поэтому все три имени обязательны на
каждом уровне: в БД (`NOT NULL`), в API (валидация DTO) и в форме админки.

**Что нужно сделать фронтенду:**

1. Заменить один инпут «Название» на **три инпута** (RU / UZ / EN) в формах
   создания и редактирования категории.
2. Блокировать сабмит, пока хотя бы одно из трёх полей пустое, и подсвечивать
   незаполненные.
3. Везде, где сейчас показывается `name`, показывать имя на языке интерфейса
   оператора (`nameRu` / `nameUz` / `nameEn`). **`name` не показывать
   пользователю никогда.**

## 2. Изменение контракта API

### 2.1 Поля объекта категории (ответ любого GET/POST/PATCH)

Узел категории теперь содержит:

| Поле | Тип | Описание |
|---|---|---|
| `id` | `string` | PK **и** slug. Генерируется сервером, клиент его не отправляет. **Не меняется при переименовании** — на него можно ссылаться. |
| `nameRu` | `string` | Название на русском. **Всегда присутствует, никогда не пустое.** |
| `nameUz` | `string` | Название на узбекском (**латиница**). Всегда присутствует. |
| `nameEn` | `string` | Название на английском. Всегда присутствует. Из него выводится slug при создании. |
| `name` | `string` | **Внутреннее** каноническое имя. Не показывать и не давать редактировать. |
| `slug` | `string \| null` | Уникальный. `null` только у легаси-строк. |
| `parentId` | `string \| null` | `null` = корень. |
| `level` | `number` | **Выводится сервером**, клиент не отправляет. 0 = корень, 1 = основная категория, 2 = подкатегория. |
| `sortOrder` | `number` | Порядок среди соседей. |
| `iconKey`, `color` | `string \| null` | Оформление плитки в покупательском приложении. |
| `isActive` | `boolean` | Мягкое скрытие. |
| `mainCategory` | `enum \| null` | Легаси-зеркало енама, только у 12 канонических строк. |
| `mxik`, `packageCodeSingle`, `packageCodeSet` | `string \| null` | Фискальные коды — без изменений, см. основную спеку. |
| `fiscalConfigured`, `fiscalByOilType`, `offersPackageChoice` | `boolean` | Производные — без изменений. |
| `productsCount`, `listingsCount` | `number` | Счётчики для guard'а удаления — без изменений. |

> **Важно про `id`:** ничто в системе не завязано на названия. Переименование
> категории на любом языке безопасно и мгновенно видно и в боте, и в приложении.

### 2.2 Правила валидации на сервере

| Ситуация | `POST` | `PATCH` |
|---|---|---|
| Поле отсутствует | **400** | OK (частичное обновление) |
| `""` (пустая строка) | **400** | **400** |
| `"   "` (только пробелы) | **400** | **400** |
| `null` | **400** | **400** — очистить имя нельзя |
| Больше 160 символов | **400** | **400** |
| Не строка (число, объект, массив) | **400** | **400** |
| Пробелы по краям валидного имени | OK — сервер обрежет | OK — сервер обрежет |

Дополнительно:

- Значения **тримятся до** проверки, поэтому фронтенду **не нужно** тримить
  перед отправкой (но и не повредит).
- **`null` не очищает имя** — в отличие от фискальных полей, где `null` это
  штатная операция очистки. У имени операции «очистить» не существует.
- Отправка поля, которого нет в DTO, — тоже **400**: глобальный
  `ValidationPipe` работает с `whitelist: true, forbidNonWhitelisted: true`.
  В частности, **не отправляйте `level`**.

### 2.3 `nameUz` — только узбекская латиница (НОВОЕ)

У `nameUz` есть дополнительное правило, которого **нет** у `nameRu` и
`nameEn`: значение должно быть написано **латиницей**. Причина — реальная
ошибка операторов: русское название вставляют в узбекское поле, и покупатель с
языком `uz` видит кириллицу.

| Значение | Результат |
|---|---|
| `Tormoz kolodkalari` | OK |
| `Oldingi tormoz kolodkalari` | OK |
| `Motor moyi` | OK |
| `ABS sensor` | OK |
| `4WD ehtiyot qismi` | OK |
| `Euro-5`, `12V`, `Mator 1.6` | OK — цифры, дефис, точка разрешены |
| `O'zbekiston` / `Oʻzbekiston` | OK — **любая** форма апострофа |
| `Gʻildirak` | OK |
| `Тормоз колодкалари` | **400** — кириллица |
| `Тормоз` | **400** |
| `Tormoz колодкалari` | **400** — смешанная строка |
| `Motor масло` | **400** |
| `O'zбек тормоз` | **400** |
| `123`, `---` | **400** — нет ни одной буквы |

**Что разрешено:** буквы `A–Z` / `a–z`, цифры, пробел, дефис, слэш, точка,
запятая, скобки, `&`, `+`, `%` и апостроф в любой из семи форм —
`'` `‘` `’` `ʻ` `ʼ` `` ` `` `´` (все они считаются одной и той же буквой,
это `Oʻ` / `Gʻ` и тутуқ белгиси). Строка нормализуется в NFC перед проверкой.

**Что запрещено:** любая нелатинская буква — кириллица в первую очередь, но
также арабица, греческий, CJK. **Одной** кириллической буквы достаточно для
400: именно так выглядит недопереведённое название.

**Сообщение об ошибке:**

```text
nameUz must contain only Uzbek Latin characters
```

Правило применяется одинаково на `POST` (поле обязательно) и на `PATCH`
(поле необязательно, но если прислано — проверяется). Пустой `PATCH {}`
по-прежнему валиден.

> Правило проверяет **скрипт**, а не орфографию: `Tormoz kolodkalari` и
> `Qwerty zzz` одинаково пройдут. Задача — поймать не тот алфавит, а не
> проверить узбекский язык.

## 3. Требования к форме (создание и редактирование)

### 3.1 Три поля ввода

Три отдельных текстовых инпута, в этом порядке:

| Метка в UI | Поле в запросе | Плейсхолдер | Обязательное |
|---|---|---|---|
| Название (RU) | `nameRu` | `Турбокомпрессоры` | ✅ |
| Nomi (UZ) | `nameUz` | `Turbokompressorlar` | ✅ |
| Name (EN) | `nameEn` | `Turbochargers` | ✅ |

- Каждое поле помечено индикатором обязательности (`*`).
- **Узбекский — латиница** (`Turbokompressorlar`, а не `Турбокомпрессорлар`):
  именно в этом скрипте оба приложения поставляют локаль `uz`. Стоит написать
  это подсказкой под полем.
- Под полем EN — подсказка, что из него формируется slug (и, следовательно,
  `id`) при создании, если явный `slug` не передан.
- Поля `name` в форме **быть не должно**. Сервер сам заполнит его из `nameEn`.

Примерный макет:

```
┌─ Категория ─────────────────────────────────────────────┐
│ Название (RU) *   [ Турбокомпрессоры              ]     │
│ Nomi (UZ) *       [ Turbokompressorlar            ]     │
│                     латиница                             │
│ Name (EN) *       [ Turbochargers                 ]     │
│                     из этого поля формируется slug       │
│ Родитель          [ Двигатель                  ▾ ]      │
│ …                                                        │
│                          [ Отмена ]  [ Сохранить ]      │
└─────────────────────────────────────────────────────────┘
```

### 3.2 Правила клиентской валидации

Обязательны, **до** отправки запроса:

1. **Все три поля обязательны.** Поле считается незаполненным, если после
   `trim()` оно пустое (`""` и `"   "` эквивалентны).
2. **Сабмит заблокирован** (`disabled`), пока хотя бы одно из трёх полей
   незаполнено. Не полагайтесь на 400 от сервера, чтобы это обнаружить — это
   должно быть видно до нажатия.
3. **Подсветка ошибки inline** у конкретного поля: красная рамка + текст под
   полем, например «Заполните название на этом языке».
4. **Момент валидации:** на `blur` и на `submit`, **не** на каждое нажатие
   клавиши — иначе наполовину набранное имя будет мигать ошибкой.
5. **Ограничение длины:** `maxLength = 160` на самих инпутах, чтобы 400 по
   длине был недостижим.
6. **Редактирование:** префилл из `nameRu` / `nameUz` / `nameEn` узла. Очистка
   поля и сохранение — это 400, поэтому блокируется тем же правилом, что и при
   создании.

7. **`nameUz` — только латиница** (см. [§2.3](#23-nameuz--только-узбекская-латиница-новое)).
   Проверяйте на клиенте, иначе оператор узнает об ошибке только из 400.
   Текст ошибки: «Только узбекская латиница — кириллица недопустима».

Опорная реализация (React Hook Form; адаптируйте под свой стек):

```ts
const NAME_FIELDS = ['nameRu', 'nameUz', 'nameEn'] as const;

const rules = {
  required: 'Заполните название на этом языке',
  maxLength: { value: 160, message: 'Максимум 160 символов' },
  validate: (v: string) =>
    v.trim().length > 0 || 'Заполните название на этом языке',
};

// Тот же алфавит, что и на сервере (common/uzbek-latin.util.ts).
// Апостроф — любая из семи форм; они считаются одной буквой (Oʻ / Gʻ).
const UZ_APOSTROPHES = "'\u2018\u2019\u02BB\u02BC`\u00B4";
const UZ_DISALLOWED = new RegExp(
  `[^A-Za-z0-9 \\-\u2013\u2014/\\\\.,:;()«»"&+%°×x*_\\[\\]${UZ_APOSTROPHES}]`,
  'u',
);

const isUzbekLatin = (raw: string): boolean => {
  const v = raw.normalize('NFC').trim();
  return v !== '' && /[A-Za-z]/.test(v) && !UZ_DISALLOWED.test(v);
};

const uzRules = {
  ...rules,
  validate: (v: string) =>
    v.trim().length === 0
      ? 'Заполните название на этом языке'
      : isUzbekLatin(v) || 'Только узбекская латиница — кириллица недопустима',
};

const isSubmitDisabled =
  NAME_FIELDS.some((f) => !(watch(f) ?? '').trim()) ||
  !isUzbekLatin(watch('nameUz') ?? '');
```

> Клиентская проверка — для UX. Источник истины остаётся серверным: если
> регулярки разойдутся, победит сервер (400). При расхождении правьте клиент
> под `Backend/src/common/uzbek-latin.util.ts`, а не наоборот.

### 3.3 Отображение категорий в списке / дереве

- Название узла берётся по языку интерфейса оператора:
  `{ ru: node.nameRu, uz: node.nameUz, en: node.nameEn }[uiLang]`.
- Полезно показать в строке/тултипе все три имени — оператору сразу видно, где
  перевод отсутствует по смыслу (например, скопирован из русского).
- Поиск по дереву стоит вести по всем трём именам сразу.
- Сортировка на сервере — по `level`, затем `sortOrder`, затем внутреннему
  `name`; если нужен алфавитный порядок по языку оператора, сортируйте на
  клиенте.

## 4. Обработка ошибок backend'а

Форма ответа при любом не-2xx (без изменений):

```json
{ "code": "VALIDATION_FAILED", "message": "...", "requestId": "3AA7FC" }
```

| `code` | HTTP | Когда |
|---|---|---|
| `VALIDATION_FAILED` | 400 | Отсутствует/пустое/`null`/слишком длинное имя; неслагифицируемый `nameEn`; цикл в дереве;наполовину настроенные фискальные данные |
| `UNAUTHORIZED` | 401 | Нет/протух админский токен |
| `FORBIDDEN` | 403 | Роли недостаточно |
| `NOT_FOUND` | 404 | Нет такой категории или родителя |
| `CONFLICT` | 409 | Slug занят; удаление заблокировано ссылками |

**Ключевое ограничение:** возвращается **только первая** проблема валидации, и
`message` — **не** стабильный контракт по полям. Не парсите текст, чтобы
привязать ошибку к инпуту, и не рассчитывайте на массив ошибок по полям.

Рекомендуемая обработка:

1. Клиентская валидация (§3.2) не даёт дойти до сервера с пустым именем —
   в норме этого 400 быть не должно вообще.
2. Если 400 всё же пришёл — покажите **тост/баннер** с сырым `message` плюс
   мелкой строкой `Request ID: <requestId>` для поддержки.
3. Форму **не сбрасывайте**: пользователь должен исправить и отправить снова.
4. `409` на slug — отдельный кейс: предложите задать `slug` вручную.

Тексты `message`, которые сервер отдаёт для имён (для понимания, не для
парсинга):

```
nameRu is required and cannot be empty
nameUz is required and cannot be empty
nameEn is required and cannot be empty
nameRu cannot be empty            // на PATCH
Could not derive a slug from nameEn — pass an explicit latin slug
```

## 5. Примеры запросов

> Базовый путь — **`/v1/admin/categories`** (не `/v1/categories`: последний —
> публичный покупательский эндпоинт и на запись не работает). Требуется
> **админский** bearer-токен; токен мобильного пользователя отклоняется.
> Роли: `SUPER_ADMIN`, `MANAGER`, `OPERATOR`.

### 5.1 Создание — `POST /v1/admin/categories`

```http
POST /v1/admin/categories
Authorization: Bearer <admin access token>
Content-Type: application/json

{
  "nameRu": "Турбокомпрессоры",
  "nameUz": "Turbokompressorlar",
  "nameEn": "Turbochargers",
  "parentId": "engine-system",
  "sortOrder": 3,
  "iconKey": "engine",
  "color": "#4285F4"
}
```

Обязательные поля: `nameRu`, `nameUz`, `nameEn`. Всё остальное опционально.
`slug` можно передать явно, иначе он выводится из `nameEn`. `level` **не
передаётся** — сервер вычислит `parent.level + 1`.

```jsonc
// 201 Created
{
  "success": true,
  "data": {
    "id": "turbochargers",
    "name": "Turbochargers",
    "nameRu": "Турбокомпрессоры",
    "nameUz": "Turbokompressorlar",
    "nameEn": "Turbochargers",
    "slug": "turbochargers",
    "parentId": "engine-system",
    "level": 1,
    "sortOrder": 3,
    "iconKey": "engine",
    "color": "#4285F4",
    "isActive": true,
    "mainCategory": null,
    "mxik": null,
    "packageCodeSingle": null,
    "packageCodeSet": null,
    "fiscalConfigured": false,
    "fiscalByOilType": false,
    "offersPackageChoice": false,
    "productsCount": 0,
    "listingsCount": 0
  }
}
```

Ошибка при отсутствующем имени:

```jsonc
// POST { "nameRu": "Турбокомпрессоры", "nameUz": "Turbokompressorlar" }
// 400 Bad Request
{
  "code": "VALIDATION_FAILED",
  "message": "nameEn is required and cannot be empty",
  "requestId": "3AA7FC"
}
```

Ошибка при пустой строке — та же самая:

```jsonc
// POST { "nameRu": "  ", "nameUz": "Turbokompressorlar", "nameEn": "Turbochargers" }
// 400 Bad Request
{
  "code": "VALIDATION_FAILED",
  "message": "nameRu is required and cannot be empty",
  "requestId": "9C1B04"
}
```

### 5.2 Редактирование — `PATCH /v1/admin/categories/:id`

Частичное: пишется только то, что прислали. Можно править один язык.

```http
PATCH /v1/admin/categories/turbochargers
Authorization: Bearer <admin access token>
Content-Type: application/json

{ "nameUz": "Turbo kompressorlar" }
```

```jsonc
// 200 OK — узел целиком, с обновлённым именем
{ "success": true, "data": { "id": "turbochargers", "nameRu": "Турбокомпрессоры",
  "nameUz": "Turbo kompressorlar", "nameEn": "Turbochargers", /* … */ } }
```

Обновление всех трёх сразу — обычный кейс формы редактирования:

```http
PATCH /v1/admin/categories/turbochargers
{
  "nameRu": "Турбины",
  "nameUz": "Turbinalar",
  "nameEn": "Turbines"
}
```

Попытка стереть имя:

```jsonc
// PATCH { "nameRu": "" }        → 400 VALIDATION_FAILED "nameRu cannot be empty"
// PATCH { "nameRu": null }      → 400 VALIDATION_FAILED
// PATCH { "nameRu": "   " }     → 400 VALIDATION_FAILED "nameRu cannot be empty"
```

### 5.3 Чтение

Без изменений в путях, узлы просто содержат три имени:

```http
GET /v1/admin/categories/tree        # всё дерево с productsCount/listingsCount
GET /v1/admin/categories?level=1     # плоский список с фильтрами
GET /v1/admin/categories/:id         # один узел
```

## 6. Готовые переводы

В корне репозитория лежит **`category_translations.json`** — всё засеянное
дерево (79 категорий) с `name_ru` / `name_uz` / `name_en`, в двух формах:

- `categories` — вложенное дерево (корни → потомки);
- `flat` — плоская мапа `id → { name_ru, name_uz, name_en }` для быстрых
  подстановок.

Файл **генерируется** из тех же модулей, из которых пишут сиды
(`npm run export:category-translations` в `Backend/`), поэтому он не может
разойтись с тем, что окажется в базе. Руками его не редактируют: правка
переводов — в `Backend/src/prisma/seed-data/category-names.seed.ts`.

Существующие категории **уже переведены**: миграция переименовала прежние
колонки `title_ru`/`title_uz` в `name_ru`/`name_uz` (сохранив все введённые
ранее переводы) и заполнила `name_en` из `name`. Отдельная кампания по вводу
данных перед выкатом формы не нужна.

- [ ] `maxLength=160` на инпутах
- [ ] В форме **нет** поля `name`
- [ ] `level` и `id` **не отправляются** при создании
- [ ] Подсказка «латиница» под UZ и «из этого поля формируется slug» под EN
- [ ] Дерево/список показывают имя по языку интерфейса, а не `name`
- [ ] Поиск по дереву ищет по всем трём именам
- [ ] 400 показывается тостом с `message` + `requestId`, форма не сбрасывается
- [ ] 409 по slug предлагает задать slug вручную

---

## 8. Чего делать НЕ нужно

- Не показывать и не редактировать `name` — он внутренний.
- Не отправлять `level` (400, поле не в whitelist).
- Не привязывать 400 к конкретному инпуту парсингом текста `message`.
- Не кэшировать категории дольше запроса — сервер сам сбрасывает свой кэш при
  записи, и бот подхватывает изменение на следующем чтении.
- Не добавлять поле «язык» в саму категорию: язык — свойство пользователя, а не
  категории. У категории всегда есть все три имени сразу.

## 9. Порядок выката

1. Применить миграцию `20260818000000_category_i18n_and_seller_lang`
   (переименование `title_ru`/`title_uz` → `name_ru`/`name_uz`, добавление
   `name_en`, `NOT NULL`, плюс `sellers.lang` для языка Telegram-бота).
2. Задеплоить backend.
3. Задеплоить фронт админ-панели с тремя полями.

Миграция и backend совместимы «сверху вниз»: старый фронт, отправляющий только
`name`, начнёт получать **400** сразу после шага 2 (три имени обязательны), —
поэтому шаги 2 и 3 стоит выкатывать вместе или с минимальным разрывом.
Обратное направление безопасно: новый фронт против старого backend'а получит
400 на нераспознанные поля, но данные не испортит.
